# Author tasks and steps

1. Discover reusable tasks, plugins, capabilities and environments by keyword. Plugin installation/loading does not prove external dependencies, credentials or target availability. Environment discovery reveals names and types, not values.
2. Describe the chosen task's summary/flow/variables or selected capability's schemas. Discover operation names rather than inventing SDK methods or action IDs. Common authoring operations include `task.create`, `step.save`, `task.flow.save`, `sequence.save` and `plan.generation.parse`; get each current Schema before use.
3. Request `author(operation="materials", params={task_id|step_id|plan_id:..., capability_ids:[...]})`. The frozen material includes baseline, runtime API, allowed builtins, live package/step schemas, control-flow guide, selected actions and plugin authoring contributions. A large response returns a bundle manifest: inspect only relevant bundle sections with paging. A selected capability may require its plugin contribution as well as its action Schema.
4. Capture live context only when the goal needs it. Discover context operations and context_provider summaries, then describe the provider to read its request_contract (required fields, defaults, target and recording declarations). Plugin detail/materials expose context_requests and declared config_variables. Context reads omit images by default; include images only when visual reasoning requires them. Recording/capture can interact with the target and must use the intended owner/environment/session.
5. Write candidates against those contracts. Use task inputs/environment references for configuration and secret references for credentials. Keep baseline/bundle ownership intact; conflicts require refreshed material and reconciliation with the user's existing work. Validate generated packages with `candidate.validate` before `task.import`; error diagnostics block a valid-candidate claim.
6. Save, trial and confirm through existing lifecycle. `step.trial` tests one action; `step.trial.flow` tests a path. Confirm each current step using matching successful evidence (`step.confirm`) or an explicitly justified manual confirmation. A path that did not visit a branch does not validate that branch. Test both outcomes with appropriate samples and verify actual attempt paths. Then confirm the current flow with `task.flow.confirm`; step confirmation and flow confirmation are distinct.

TaskWeave supports linear task-2 and control-flow task-3 packages, conditions, foreach, while/until, nested branches/loops and task sequences with repeated task nodes. Fetch the current flow guide and schemas from materials for exact structure, loop bounds, binding scopes and output rules. Let the executor schedule iterations and branches. Every sequence node has its own identity even when task IDs repeat. Preserve these identities in bindings and acceptance sources.

For revised code, repeat validation of affected steps/paths and the resulting definition. Prepare acceptance requirements for the final version before starting a formal run.
