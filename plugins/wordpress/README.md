# WordPress

Optional `uv sync --locked --extra wordpress` package, plugin API v1, version 0.1.0. The core's default dependencies and task/database formats are unchanged. The package depends on the reusable process and SSH libraries; enabling SSH/process actions is not required.

Configure `wordpress_site_path`, `wordpress_mode` (`local`, default, or `ssh`), optional `wordpress_wp_path` (default `wp`) and `wordpress_php_path`. Local paths must resolve under `wordpress_local_root` (default site root). SSH uses its own `wordpress_ssh` object with host/port/username, mandatory trusted `known_hosts`, explicit `remote_root`, key/password secret references, and opt-in agent settings from the SSH library. `role` identifies independently owned resources; concurrent open or execution on the same role fails before a second handle/write. Different roles can execute concurrently and retain separate receipts.

The plugin executes typed argv without a local shell; SSH quotes each token through the trusted server. It does not add allow-root, force, insecure flags, arbitrary PHP evaluation, or install missing user tools. PHP, WP-CLI, and database clients must already exist. The tested profile is WP-CLI 2.12.0; the positional config-secret transcript specifically requires this version. CLI `check_environment` reports its actual PHP/MySQL paths/versions, and distinguishes that observation from database usability. Installed-state false is accepted only for a complete silent exit 1 after independent core/config/`SELECT 1` prerequisites; diagnostic/authentication/PHP failures remain errors.

`wordpress_secret_refs` maps environment variable names to logical references. Password fields use `admin_password_ref`, `db_password_ref`, `password_ref` or config `value_ref`; the context resolves them through `ctx.resolve_secret`. Values go through stdin, never plugin argv or stored receipts. Config secrets use the pinned six-line bare-prompt transcript; even quiet WP-CLI echoes these values, so capture redacts before clipping. Empty, literal `0`, multiline/NUL, and over-1023-byte prompt values fail before spawn. Config secret postchecks return `secret_matches`, never plaintext or password hashes. Config/option getters reject password, key, salt, token and other secret-named fields. Literal masking is not a general scrubber for arbitrary business content.

Actions are independent and reject unknown input fields:

| Group | Actions | Main targets |
| --- | --- | --- |
| Core | check_environment, is_installed, core_download, core_install, core_update, verify_checksums | version/locale; install URL/title/admin refs |
| Config | config_create, config_get, config_set, option_get, option_set, set_permalink_structure | name/type or option key; typed option JSON stdin |
| Themes | list_themes, install_theme, activate_theme, update_theme, delete_theme | explicit slug/version; optional ZIP/URL source with expected slug |
| Plugins | list_plugins, install_plugin, activate_plugin, deactivate_plugin, update_plugin, delete_plugin | slug/version, explicit network scope for activation |
| Posts/pages | list_posts, create_post, update_post, delete_post | id, post_type, title/status/content; content stdin |
| Terms | list_terms, create_term, update_term, delete_term | taxonomy/id/name/parent |
| Menus | list_menus, create_menu, delete_menu, add_menu_item, update_menu_item, delete_menu_item | menu id, item id; post/term/custom variant and same-menu parent |
| Media | list_media, import_media, update_media, delete_media | attachment id or confined source/explicit URL; title/caption/description/alt |
| Users | list_users, create_user, set_user_role, set_user_password, delete_user | typed id/login/email/role and explicit content disposition |

All names carry `wordpress.`. Only environment/installed/checksums/config_get/option_get/list actions are READ. Every other action is WRITE, including search preview; writes never automatically retry. Lists default to 20, maximum 100, with offset and conservative `truncated`/`next_offset`. Native query lists use finite WordPress query limits; theme/plugin/menu lists are captured under the output ceiling and sliced only after complete JSON parsing. A clipped JSON response is failure. Active themes/parents/plugins cannot be silently deleted; same-state operations return `noop`. Final-administrator removal is protected. Post delete defaults to Trash; media delete is permanent. Metadata updates never pretend to replace attachment bytes or generated image sizes.

Timeout defaults to 60 seconds (1–1800) and covers owned connection acquisition, preflight, all command/file stages and postchecks. Output defaults to 64 KiB per process stream (1 KiB–1 MiB); the final JSON envelope also obeys the selected output ceiling. File transfers default to 16 MiB and maximum 64 MiB, configured by action `max_bytes` or `wordpress_max_transfer_bytes`. Complete reads fail at the boundary rather than silently clipping SQL/archives.

`wordpress_owned_tables` is an explicit finite list authorized for this site's configured table prefix. Every database/search/backup action requires caller `tables` to be a subset of it and of actually observed database tables. Imports send the exact validated bytes through WP-CLI 2.12 `db import - --binary-mode --skip-optimization`, with a fixed initial SQL mode; no SOURCE or arbitrary client options are exposed. All client metacommands outside quoted literals are refused, including binary mode's remaining charset/delimiter commands. MySQL/MariaDB executable comments are supported only as complete standalone native-dump SET metadata or ALTER TABLE … ENABLE/DISABLE KEYS statements, with an independent statement boundary after each comment. Each entire payload is validated; executing it affects only safe session metadata or an owned table, while skipping it is an empty statement. Conditional fragments in table names, CREATE bodies/options, values or surrounding SQL are refused regardless of version; the plugin never guesses which version branch a server executes. Only native exports remove the exact MariaDB dump leading sandbox directive before validation and output; external imports never rewrite bytes. CREATE consumes a finite grammar of scalar columns, owned-column indexes and unique table options, rejecting expression clauses and unknown options. The SQL surface accepts bounded ordinary table-dump grammar, including MariaDB session metadata and transaction markers; it rejects database switches, unrelated tables, views/routines/triggers, foreign-key references, external engines/storage paths and arbitrary SQL. Unsupported dumps fail rather than being treated as complete backups. Dedicated or shared database use both require explicit table scope; whole-database import/drop is never a default.

Backup includes every bounded regular site file, hidden files, directory modes/empty directories, wp-config, SQL, canonical site URL/root/database/prefix/version identity and SHA-256 manifest. Symlinks and special files are refused. Explicit external config/content/upload roots are unsupported and fail the full-backup request. `max_unpacked_bytes` independently bounds expanded member content (default 256 MiB, maximum 512 MiB); `max_members` defaults to 10000, maximum 100000, including manifest/SQL/directory entries. These new 0.1.0 fields do not change core storage/contracts. Compressed package and each complete member still obey `max_bytes`. The full gzip footer/CRC, member paths/types/duplicates/sizes/hashes, identity/table scope and decompression/member budgets are validated before restoration writes. SQL and file snapshots are sequential; external writers must be quiesced for a consistent snapshot. Temporary export/import SQL lives in plugin-created 0700 OS temporary directories with 0600 staged files, outside the site snapshot. Cleanup evidence reserves one of the existing 96 attempt slots before creating a temporary directory. A full journal refuses before scratch creation; later capacity/cancellation failures still attempt cleanup using the reserved slot, without dispatching a new receipt. Cleanup reservation appears before its native command in sequence order and its final completion is updated without replacing any business stage. Failed cleanup stops the operation and leaves a bounded unknown cleanup receipt alongside prior write evidence; a protected leftover may require operator cleanup.

Archive handling currently retains expanded file/member content plus the compressed envelope in RAM; validation and construction can hold several simultaneous buffers, with memory well above the selected expanded quota. Allow several times `max_unpacked_bytes` plus Python/file metadata and application/tool headroom; the 512 MiB maximum and 100000 members are ceilings, not a promise that a 1 GiB host can process them. Concurrent snapshots on different roles multiply aggregate RAM demand. There is no aggregate memory admission guard: operators should serialize large backup/restore actions and provision headroom before allowing concurrent roles. Approved complete-site/expanded/transfer limits remain unchanged. Maximum-size and concurrent memory pressure have not been validated.

Restore applies a verified file/directory overlay then scoped SQL import and target checks. It does not delete extra destination files, offer rollback, or claim atomicity. Each attempt retains bounded cumulative write receipts across actions, later reads/script errors and concurrent roles. File restoration has a completed-file counter and a hash identifying any pending file; completed/partial/unknown stages persist through `wordpress.operation_failure` before resource close. Captures contain action/role/stage and safe bounded diagnostics, never command arguments or stdin. Capacity (32 attempts, 128 resource owners, 96 write stages per attempt) fails before new writes. A failed run remains failed/UNKNOWN even when earlier commands completed.

Search replacement defaults to dry-run, serialization-aware literal replacement, explicit tables and `guid` exclusion. It returns a count and preview token bound to full site identity, OLD/NEW, tables/columns, count and impact budget. Execution requires `dry_run=false`, the same resource's fresh preview (five minutes), another matching dry-run and the count cap; mismatch after execution remains failure with write evidence. External writers can change state between the probe and write, so this is not an atomic global replacement limit. Cache flushing requires the caller's explicit `exclusive_cache=true` assertion; this cannot verify an external cache topology.

`wordpress.site` context supplies passive bounded version/theme/plugin/page summaries. Use `ctx.output("wordpress.file", "site_backup", result["artifact"])` inside `ctx.result(outputs=[...])` to save credential-bearing archives through the host's file handler, or `wordpress.json` for ordinary structured results. No secret-bearing file is returned inline.

Focused verification: `uv run --extra wordpress python -m unittest tests.test_wordpress tests.test_devops_discovery -v`. Explicit real tests require `TW_WORDPRESS_INTEGRATION_CONFIG` and `tests.test_wordpress_integration`; they do not create/install tools/containers. Local acceptance runs actual Python TaskWeave with PHP/WP/database clients in the isolated fixture; SSH acceptance uses a real pinned OpenSSH server with independently trusted host key. Protocol executables and worker failure tests are separate evidence, never full WordPress acceptance.

READ marks native command business intent, not a guarantee that WordPress bootstrap/plugins/caches/cron never write. In the owned upgrade acceptance fixture, all prior table/file checks matched immediately after upgrade, but a later `wp db tables` bootstrap verifier was followed by a tw_options checksum change. The exact changed rows were not established; that observation remains evidence and was not silently restored. No user production data was involved. Use independently verified before_wp_load database queries when proving read-only state boundaries, and distinguish verification time from final state.

Theme/plugin archive installation and media import resolve non-URL sources against the configured local_root/SSH remote_root. The validated canonical absolute path is passed to WP-CLI even when site_path is a subdirectory; CLI cwd remains the site. Site-relative sibling files or symlinks cannot replace the checked configured-root source merely through relative argv. Caller input objects, URL sources and expected extension slug semantics remain intact. This preserves existing path validation and does not claim an atomic filesystem TOCTOU guard.
