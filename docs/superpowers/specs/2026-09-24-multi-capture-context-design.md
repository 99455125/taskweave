# 插件上下文多次采集设计

日期：2026-09-24\
状态：基础数据设计已实施；交互与保存时机以顶部所链接的已确认补充设计为准。

## 目标与术语

用户可以给一组插件上下文填写一次名称和操作说明，再向该组按顺序追加多次采集。例如“合约录入”下依次采集合约类型、币种、账单周期三个下拉框的展开状态。每次采集可以独立预览、重新采集、删除和排序。规划页、步骤编写页及调试页使用相同的结构和操作。

- **上下文组**（group）：名称、操作说明、采集器和组顺序。一个组固定一个 `provider_id`；跨插件另建组。
- **采集项**（capture）：一次成功的插件采集调用，是用户可操作的最小单位。一次调用返回的完整 `ContextCollection`（一个或多个 `ContextItem` 及零个或多个 `ContextView`）都属于同一项。不要把插件返回的每个原始 `ContextItem` 当成一次用户采集。
- **预览**：属于采集项。Playwright 每项可有本次页面截图，TiDB 每项可有本次表格。组不保存或合成预览。

本功能不改变任务步骤的执行结果、结果展示契约，也不要求插件实现组、追加或删除。插件继续实现 `collect_context(provider_id, ctx, request, include_view=...) -> ContextCollection`，其 `ContextView` 渲染器仍由插件注册。

## 现状与边界

当前 `step_contexts`、`plan_contexts` 每行都是一次采集，名称/说明和 `item_json`、`views_json` 混在一行。`ContextCards` 展示一行；“重新采集”替换整行。规划生成的 `plan_context_refs` 指向这些行的 `context_id`。步骤 AI 将各行的 `item` 展平，规划 AI 按行提供上下文。

新模型将原有 `context_id` 定义为**组 ID**，另增 `capture_id` 标识每次采集。`plan_context_refs` 仍引用组 ID，因此一次引用自动包含组下全部采集项。当前开发数据通过一次数据库迁移转换为“每个旧组包含第 1 项”；迁移后只读新结构，不保留双模型兼容分支。

采用子表保存采集项，而非把多次采集塞进父行的一个大 JSON 数组：子表可以单项更新/删除、保证顺序和所属关系，也避免每次操作都重写其他项的大截图。分组不交给插件实现，因为它是规划与步骤共用的用户编写行为，不属于具体插件的采集能力。

## 持久化模型

控制库下一版本增加两张子表：`plan_context_captures`、`step_context_captures`。分别以 `context_id` 外键关联现有规划/步骤上下文组，删除组时级联删除项。每项至少包含：

| 字段 | 说明 |
| --- | --- |
| `capture_id` | 不变的项 ID |
| `context_id`、`order_index` | 所属组及组内顺序 |
| `label` | 可编辑的简短标题；未填写时显示“采集 1”等编号 |
| `request_json` | 本项传给插件的原始参数，包括插件自定义 JSON |
| `items_json`、`views_json` | 本次调用返回的完整内容及预览；严格对应同一项 |
| `include_view`、`captured_at` | 本次预览选择及采集时间 |
| `source_session_id`、`source_page` | 使用的实例和入口；适用的入口分别保存，不挪到组级别 |
| `created_at`、`updated_at` | 项创建和最后更新时刻 |

父表保留 `context_id`、所属规划或步骤、`provider_id`、`name`、`context_notes`、组顺序及创建/更新时间。原来描述单次采集的列从父表移到子表。组有自己的修订号；项变动增加组修订号，规划项变动同时增加规划修订号。步骤组及项的变动沿用现有“待确认”规则，使已确认步骤转为待确认。所有操作必须验证项确实属于所请求的组、组确实属于当前规划或步骤。

列表接口只返回组与采集项的标题、顺序、时间等摘要。展开原始内容或打开预览时再按 `capture_id` 读取该项的 `items_json` 或 `views_json`；尤其不能在列表请求中重复传输所有截图的 base64。AI 生成服务按需读取原始内容，但不读取预览数据。这样采集项增多时，页面首次加载量仍与摘要大小相关。

迁移时，每条旧上下文保留原 `context_id`、名称、说明和组顺序；其 `item_json`、`views_json`、请求、来源、时间生成一条新采集项，顺序为 0。空数组仍作为一条旧采集项保存，避免静默丢数据；新采集则拒绝既无内容也无预览的结果。迁移应在原控制库版本机制中以事务执行，并保留已有备份行为。规划复制、任务复制/导入、规划生成后的导入都需要复制完整项及顺序，复制时生成新的组/项 ID，保持内容和预览关联。

## 应用操作与事务

规划与步骤各提供同一组语义的操作：`create_group`、`update_group`、`delete_group`、`reorder_group`、`append_capture`、`replace_capture`、`delete_capture`、`reorder_capture`、`list_group_summaries`、`get_capture_content`、`get_capture_preview`。API 名称可依现有 REST/dispatch 约定调整，但操作边界不能混淆。规划写操作使用现有 `expected_revision`，步骤写操作校验组修订号；过期请求返回冲突并要求页面刷新，不覆盖其他窗口的采集。

追加流程：先调用选定插件采集器；成功且结果有效后，在单个数据库事务中追加项并更新修订号。插件失败、实例变化、预览序列化失败时不写入空项。重复采集相同页面允许，不能按内容去重。替换仅更新指定 `capture_id`，保留它的位置及创建时间，更新请求、内容、预览和采集时间。删除单项只清理该项的内容和预览；删掉最后一项时**保留空组及其名称/说明**。删除整组时再级联删除所有项。新采集项和删除项都不得修改其他项。

## 页面交互

规划与步骤共用 `ContextCards` 的两级结构：外层是“已采集的上下文”，每组显示名称、插件、项数和组操作；展开组后先显示名称/操作说明，再显示有序采集项。项标题默认“采集 1、采集 2…”，可改为“币种选项”等；每项显示采集时间、来源，以及“查看预览”“重新采集”“上移/下移”“删除”。删除项与删除整组是两个明确入口，确认文字写清实际影响。空组显示简短空状态与“追加采集”。

点“追加采集”打开现有插件参数弹窗，固定本组 `provider_id`，沿用实例选择、插件表单、高级 JSON 和预览勾选。可从上一项带入请求参数供修改，但必须再次实际调用插件。点某项“重新采集”使用该项原参数预填弹窗，成功后原位替换该项。当前页面对所有项的预览仍执行“展示时脱敏”；“发送 AI 时脱敏”设置只作用于发送副本，不改库存原文。截图、表格只在所属项的预览中展示；不生成组级拼图或组级表格。

## AI 输入与规划导入

先按组顺序，再按组内项顺序组装 AI 上下文。组名称、操作说明、插件 ID 只提供一次；每项提供标题、采集序号、时间和插件返回的原始 `items`。`views`、预览截图不因启用预览而自动加入 AI 请求；若插件有意返回 `kind=image` 的 `ContextItem`，仍按现有图像上下文规则处理。空组不发送 AI，也不能成为有效的 `plan_context_refs`。

规划生成时冻结**完整组和全部项**，而非引用可变的实时记录；后续增删项不改变已经生成的候选内容。AI 返回的 `plan_context_refs` 继续使用组 ID。导入任务时，将被引用组及其全部项复制到相应步骤；项顺序、标题、请求、内容、预览、采集时间一并保留，来源标记为规划导入。步骤 AI、调试 AI 使用同一套组装函数，不能一处按组、一处按旧展平逻辑而丢失顺序或说明。

## 插件架构要求

插件只知道一次采集请求和一次 `ContextCollection` 响应。`ContextItem` 可为多个，`ContextView` 可为多个；核心把这一整个响应作为一个采集项保存。`provider_id` 固定在组上，插件私有请求参数留在项上，核心不识别 Playwright 的 `scope/target_id` 或 TiDB 的 `table`。预览仍由插件注册的 renderer 决定。将来新增插件无需实现新的“多次采集”接口。

## 定向验收

1. 在规划建一个 Playwright 组，连续采集两个不同下拉框：得到 2 项、2 份各自的截图；AI 输入顺序一致，组名称和说明不重复铺满每项。
2. 只删除第 1 项：第 2 项内容、截图及组说明仍在；重新采集第 2 项只替换该项。删除最后一项后组仍可再次追加。
3. 步骤页和调试页读写同一组记录；追加、替换、删除、排序使步骤变为待确认。规划每次变动增加修订号，旧页面写入得到明确冲突。
4. TiDB 表结构多次采集得到逐项表格预览；OCR 或其他插件无须修改便可使用相同交互。单次插件返回多个原始 `ContextItem` 时仍只生成一个可删除采集项。
5. 规划复制、生成冻结、导入任务、任务复制后，各项内容和预览不串组、不丢顺序；删除规划、任务、步骤或整组时，子项随所属记录删除。
6. 旧数据迁移后，原每条上下文恰有一项，名称、操作说明、采集内容、预览与时间保持；没有运行时双模型回退。展示脱敏和发送 AI 脱敏分别有效。

按功能运行存储迁移、上下文操作、规划导入、页面组件及相关插件的定向测试。**不要运行全量测试**，除非用户另行确认。设计阶段不执行测试。

## 实施顺序

1. 加数据库迁移与组/项存储操作，先覆盖所有权、顺序、事务和旧数据迁移。
2. 加应用服务与 dispatch 操作；复用现有插件采集调用，保持 `ContextCollection` 契约不变。
3. 改规划和步骤/调试的上下文组装、生成冻结、导入/复制链路。
4. 改共用卡片及两处采集弹窗；接入项级预览、替换和删除。
5. 只运行受影响功能模块测试并更新相关文档；不做无关重构。
