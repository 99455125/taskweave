# AI 协作方法

需求驱动一次变化；模块文档承载变化完成后的当前知识。一个需求可以影响多个模块，一个模块也可以由多个需求逐步演进。

## 文档权责

| 内容 | 唯一维护位置 | 何时读取/修改 |
| --- | --- | --- |
| 稳定工作约束 | 根 AGENTS.md | 开工读取；规则变化才改 |
| 改哪里、读什么、测什么 | maintenance.md | 默认定位入口；模块入口变化才改 |
| 当前模块行为、约束、边界 | modules/ 对应文件 | 只读/更新受影响模块 |
| 详细协议、异常与操作契约 | reference/ 对应专题，由模块链接 | 涉及该契约才读/改；模块只保留摘要 |
| 长期取舍与后续产品范围 | decisions/；roadmap.md | 边界决策或范围变化才更新 |
| 平台交付与发布验收 | deployment.md、windows-portable.md、release-checklist.md | 打包/发布时按范围读取 |
| 全局架构与依赖方向 | architecture.md | 跨模块设计时读取 |
| 当前任务、阻塞、已知问题 | status.md | 续接、状态查询或状态变化时 |
| 测试机制和选择规则 | testing.md；实际目标为 tests/module-map.json | 选择验证范围时 |
| 本次目标、设计、验收结果 | 当前任务/PR；必要时 docs/decisions/ 或当前 REQ | 本次实施；后续只按需追溯 |
| 旧记录 | docs/archive/、已关闭 REQ、旧 superpowers 设计/计划 | 查历史决策或证据时 |

## 按改动规模记录

- 小修复、文案与局部布局：不强制新建 REQ；交付说明记录验证，当前行为变化时更新相应模块。
- 新业务能力：默认在当前任务/PR 中说明范围、验收和结果，不要求建立目录。需要跨任务持续设计时，在 `docs/decisions/` 写一份命名明确的设计记录（背景、决策、影响、验证）；只有明确要求按需求交付时才使用 REQ 目录。
- 历史 REQ 保持原文件名与证据，不为了格式统一重写。需要新建 REQ 时仅在需求索引登记主题；当前状态只维护 status.md。
- 不强制创建 code-mapping、plan、progress、validation、review 全套文件。复杂工作的独立审核记录可单独保留，不能用文档数量衡量完成度。

## 实施闭环

明确本次范围与验收 → 维护索引定位 → 核对代码 → 必要设计 → 编码 → 相关验证/审核 → 更新受影响模块现状 → 记录结果并关闭本次工作。

未完成方案保留在当前任务或必要的设计记录，不提前写成模块已有行为。完成时从需求中提炼实际规则，而非把需求全文复制到模块文档。后续维护无需阅读或同步修改其他需求目录；跨模块影响通过当前模块知识和实际代码定位。

模块文档写职责、用户可观察行为、关键不变量、源代码入口、验证入口和相关模块，不抄全部类/方法，也不复制测试映射表。精确签名、字段、DDL 以源码为准；存在冲突先核查，不静默采用旧文档。

## 跨任务交接

保留用户指定的设计、编码、审核职责。交接只包含本次目标、授权范围、当前设计/模块入口、改动位置、实际验证、未关闭问题与下一步；不要求接手者通读完整聊天或其他需求历史。

会话 ID、催办经过、临时快照路径不进入长期模块知识；确需审计时保留在本次结果或历史证据中。完成条件是范围内交付和对应验证证据，结构检查通过不等于业务功能通过。

## 知识维护完成条件

本次变化的长期规则进入对应模块或已有契约专题；摘要链接详细契约，不复制一份完整规则。未实现范围进入roadmap，已知缺陷进入status，实际测试证据留本次结果。后续维护者仅靠当前入口即可理解行为、边界和验证方式时，需求记录才能作为纯历史关闭。不要把新细节只追加在REQ进度里，也不需要每次改动更新知识迁移台账；该台账只记录2026-09-26这次迁移来源。
